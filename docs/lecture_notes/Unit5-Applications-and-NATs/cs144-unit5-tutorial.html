Application Layer Protocols

You know how to write code. But when your browser loads a web page, downloads a torrent, or assigns your laptop an IP address, what actually happens on the wire? This tutorial walks through six foundational protocols — HTTP, BitTorrent, DHCP, DNS, and NAT — from first principles. No prior networking knowledge required.

Section 01

HyperText Transfer Protocol (HTTP)

Every time you visit a URL, your browser uses HTTP — the HyperText Transfer Protocol — to ask a server for a document. HTTP is the cornerstone of the web and today powers video streaming, API calls, and single-page applications. Let's understand it from the ground up.

What is HyperText?

HyperText is a document format expressed in plain ASCII text where special tags (wrapped in <angle brackets>) carry formatting instructions. Think of it as a letter where you write <h2>Introduction</h2> and your browser knows to render the word "Introduction" as a large heading.

The killer feature of HyperText is embedding: a document can reference other documents. An <img src="photo.jpg"> tag does not store the image bytes inside the page — it tells the browser "go fetch this separate file and display it here." This means loading a single page can trigger a cascade of additional requests. Opening the New York Times homepage, for instance, results in roughly 20 separate resource downloads in the background.

The HTTP Request–Response Model

HTTP uses a client–server architecture. The client (your browser) opens a TCP connection to a server and sends a command. The most common command is GET, which asks for a resource at a given URL. The server reads the request, processes it, and writes back a response — then the cycle repeats.

Both the request and the response are human-readable ASCII. You can literally type an HTTP request by hand using the telnet tool — something no other widely-used protocol makes quite this easy.

Request Format

HTTP/1.x Request Structure
GET /fullduplex/index.html HTTP/1.1\r\n     ← request line
Host: sing.stanford.edu\r\n                 ← header
Accept: text/html\r\n                       ← header
\r\n                                         ← blank line (mandatory)
                                             ← body (empty for GET)

The first line contains three fields separated by spaces: the method (GET, POST, PUT, …), the URL path, and the protocol version. Each line ends with a carriage-return + newline (\r\n). A mandatory blank line separates the headers from the optional body (used by methods like POST that send data to the server).

Response Format

HTTP/1.x Response Structure
HTTP/1.1 200 OK\r\n                         ← status line
Content-Type: text/html; charset=utf-8\r\n  ← header
Content-Length: 4823\r\n                    ← header
\r\n                                         ← blank line
<!DOCTYPE html>...                         ← body (the actual document)

A response starts with a status code: 200 OK (success), 304 Not Modified (use your cached copy), 404 Not Found, 500 Internal Server Error, etc. These three-digit codes let clients programmatically react without parsing prose.

HTTP/1.0 and Its Speed Problem

In HTTP/1.0 the rule is simple: one request per TCP connection. After the server sends the response, it closes the connection. If your page needs ten images, you open ten connections — each paying the full cost of a TCP handshake.

Let's measure exactly how expensive that is. Assume:

ParameterValue
One-way latency50 ms
HTTP request size1 full segment (10 ms packetization delay)
HTTP response size2 full segments (20 ms packetization delay)
SYN / ACK packets0 ms packetization delay (tiny)
Max parallel connections2

Case 2: Page + 2 Images

Step 1 (the page itself) costs 230 ms just as above. Step 2 sends two parallel image requests on two separate TCP connections. Even though the connections share the same physical link — meaning their segment transmissions queue up behind each other — the important insight is that packetization delays partially mask each other: while response 1a goes out, request 2 is arriving, so response 2a queues immediately after response 1b.

Notice: even loading just 2 images more than doubles the page load time — largely because we paid the 100 ms TCP handshake cost again just to start those image requests.

Key Takeaway

HTTP/1.0's one-request-per-connection model forces a full TCP handshake (100 ms at 50 ms RTT) before every burst of resources. This overhead compounds badly as pages embed more and more assets. Every repeated setup also restarts TCP's congestion window from scratch, preventing the network from warming up.

Section 02

HTTP/1.1 Keep-Alive & Pipelining

HTTP/1.1 introduced one of the most impactful optimizations in the history of the web: persistent connections, controlled by the Connection: keep-alive header. Instead of tearing down the TCP connection after each response, the server keeps it open so the client can reuse it for subsequent requests.

The Keep-Alive Handshake

The negotiation works through two headers:

  • 1 The client includes Connection: keep-alive in its request header, hinting "please leave this connection open after you respond."
  • 2 The server responds with Connection: keep-alive (or Connection: close if it refuses). It may also send a Keep-Alive: timeout=60 header indicating how long it will maintain the idle connection.
  • 3 The client sends further requests on the same TCP connection, skipping the handshake entirely.

Concrete Speed Comparison

Let's run the numbers with more realistic assumptions: 50 ms latency, 1 ms packetization delay (a fast link), and a page that loads 11 images.

PhaseHTTP/1.0HTTP/1.1
TCP handshake(s)100ms × 7 rounds = 700ms100ms × 1 = 100ms
Page request/response103ms103ms
11 image requests6 × 203ms = 1218ms~123ms (pipelined)
Total1,421 ms326 ms

HTTP/1.1 is 4× faster in this scenario. The dramatic gain comes from two sources. First, we pay the TCP handshake only once. Second, we can send all 11 image requests back-to-back on the open connection without waiting for each to fully complete before sending the next — a technique called request pipelining.

HTTP/1.1 — Pipelined Requests on One Connection
Client                                    Server
  │─── TCP handshake (100ms) ───────────── │
  │─── GET /page ───────────────────────►  │
  │◄─── 200 OK /page ───────────────────── │
  │─── GET /img1 ───────────────────────►  │   ← no new handshake!
  │─── GET /img2 ───────────────────────►  │   ← pipelined immediately
  │─── GET /img3 ──  ...                   │
  │◄─── img1 response ──────────────────── │
  │◄─── img2 response ──────────────────── │
  │◄─── img3 response ──────────────────── │

Why Persistent Connections Also Help Congestion Control

TCP's congestion control algorithm (AIMD / slow start) begins each new connection with a tiny window. The window must be earned by sending packets without drops. HTTP/1.0 resets this learning with every new connection. HTTP/1.1 lets the window carry over across multiple requests on the same connection, so later requests in a session enjoy a warmed-up, larger congestion window and therefore higher throughput.

SPDY and HTTP/2

HTTP/1.1's pipelining has a subtle problem: responses must be delivered in the same order as requests. If a slow-to-generate page is requested first, images must wait — a phenomenon called head-of-line blocking. Google's SPDY protocol (later standardized as HTTP/2) solved this with:

  • →Multiplexed streams: multiple logical request/response pairs interleaved on one connection, so a slow resource doesn't block fast ones.
  • →Header compression: browsers send largely identical headers (User-Agent, Accept, cookies) on every request; SPDY compresses these, saving meaningful bytes on mobile.
  • →Server push: a server can proactively send resources it knows the client will need, before the client even asks.
Key Takeaway

Keep-Alive eliminates per-resource TCP setup cost and allows pipelining. On a page with many assets, this single change produces 4× speed improvements. HTTP/2 goes further by eliminating head-of-line blocking and adding header compression — both building on the same insight: share one long-lived, well-warmed TCP connection rather than opening many short ones.

Section 03

BitTorrent: Peer-to-Peer File Sharing

HTTP is excellent for fetching documents from a server — but if millions of people want the same large file simultaneously, a single server becomes a bottleneck. BitTorrent's solution: turn every downloader into an uploader, distributing both the storage and the bandwidth across a self-organizing network of peers.

Swarms and Pieces

A BitTorrent swarm is the collection of all clients currently downloading or seeding a particular file. The file is broken into fixed-size pieces (typically 256 KB–1 MB). Why pieces instead of one big stream?

  • 1Parallelism: you can download piece 1 from Alice, piece 2 from Bob, and piece 3 from Carol simultaneously.
  • 2Incremental sharing: as soon as you finish a piece, you can start uploading it to others — even before the full file is done.
  • 3Integrity checking: each piece has a SHA-1 cryptographic hash in the .torrent file, so you can verify every piece independently after download.

Pieces are further subdivided into smaller subpieces, allowing simultaneous download of different parts of the same piece from different peers, reducing latency to obtain any one piece.

Finding Peers: Trackers and DHT

To join a swarm, a client needs to know who else is in it. Historically this was done through a tracker — a central server listed in the .torrent file. A client announces itself to the tracker and gets back a list of peer IP:port pairs.

After trackers attracted legal attention, BitTorrent migrated to trackerless torrents using a Distributed Hash Table (DHT). A DHT maps a file's info-hash to the set of peers sharing it, but the mapping is stored collectively across all participating nodes — no single server holds the full picture. Think of it as a distributed phone book: any node can look up any entry by asking its neighbors, who ask their neighbors, until the answer is found.

What to Download: Rarest First

Peers continuously exchange bitfields — bitmaps indicating which pieces each client currently holds. A smart client downloads the rarest piece first: the piece held by the fewest peers in the swarm.

Why? If only one peer has piece #47 and that peer disappears, nobody can ever complete the file. By prioritizing rare pieces, the swarm ensures that pieces spread widely before common pieces are fully replicated, maintaining overall availability.

Exception: when a client only needs its last few pieces, it requests each from multiple peers simultaneously (called the endgame strategy) to avoid getting stuck waiting for one slow peer to deliver a final piece.

Whom to Upload To: Tit-for-Tat

If you uploaded to every peer equally, each of your ~100 TCP connections would be painfully slow. Instead, BitTorrent uses a choking algorithm:

  • 1Measure the download rate you're receiving from each peer over the last 20 seconds.
  • 2Pick the P best (often P=4) — these are unchoked and receive your upload bandwidth.
  • 3Every ~30 seconds, randomly unchoke one additional peer — an optimistic unchoke — to discover potentially better partners.

This is a real-world implementation of the game-theory principle of Tit-for-Tat: cooperate with cooperators, and defect against defectors. Peers who upload get upload; peers who only leech get choked.

BitTyrant: Gaming the System

A 2007 paper introduced BitTyrant, a modified client that exploits the standard TFT algorithm: instead of giving each unchoked peer an equal share of upload bandwidth, BitTyrant gives each peer just enough to remain in their top-P list — freeing the leftover bandwidth to bribe additional peers into unchocking it. The result: a 70% median improvement in download speed for BitTyrant users. The paper also showed that if everyone used BitTyrant, performance improved slightly overall — but the biggest gains go to the selfish user when others are cooperative.

Key Takeaway

BitTorrent's three key algorithms — rarest-first piece selection, tit-for-tat upload scheduling, and optimistic unchoking — together create a self-sustaining ecosystem where contributing is rewarded, availability is maximized, and the load distributes itself across the swarm rather than concentrating on any one server.

Section 04

DHCP: Getting an IP Address Automatically

Before your laptop can send a single packet, it needs four pieces of configuration: an IP address, a subnet mask, a default gateway (the router), and a DNS server address. In the early days of the internet, a network administrator would hand these to you on a slip of paper. Today, you get them automatically in milliseconds — thanks to DHCP, the Dynamic Host Configuration Protocol (RFC 2131).

Why Dynamic Configuration?

Static assignment (typing in numbers manually) has three serious problems:

  • ✗Mobility: if you move your laptop to a different subnet, your old statically-configured address is invalid.
  • ✗Scarcity: IP addresses are finite. You don't want to permanently reserve one for a device that's only connected 8 hours a day.
  • ✗Garbage collection: there's no automatic reclamation; unused addresses accumulate and block new devices.

DHCP solves all three: addresses are temporary leases, automatically returned when they expire or the device releases them.

The DORA Exchange

The DHCP protocol follows a four-message pattern nicknamed DORA. Here's the problem it must solve first: the client has no IP address yet, so it can't send a unicast packet to anyone. DHCP's elegant solution — use UDP broadcast to destination 255.255.255.255, which reaches every device on the local network segment.

DHCP DORA Sequence
Client (no IP)          DHCP Server A          DHCP Server B
    │                        │                       │
    │─── DISCOVER ──────────►│──────────────────────►│   broadcast: "anyone there?"
    │                        │                       │
    │◄─── OFFER (10.0.0.5) ──│                       │   "I can give you 10.0.0.5"
    │◄─── OFFER (10.0.0.7) ──│───────────────────────│   "I offer 10.0.0.7"
    │                        │                       │
    │─── REQUEST (10.0.0.5) ►│──────────────────────►│   broadcast: "I'll take 10.0.0.5"
    │                        │                       │   (Server B withdraws its offer)
    │◄─── ACK ───────────────│                       │   "Confirmed, lease = 24h"
    │                        │                       │
    │     ... uses 10.0.0.5 for 24h ...
    │
    │─── RELEASE ────────────►│                      │   "I'm done with this address"

After receiving the ACK, the client has a fully configured IP address for the duration of the lease. Before the lease expires, the client sends a renewal REQUEST. If the server doesn't hear from the client and the lease expires, the address is returned to the pool.

Technical Details

DHCP runs over UDP, using port 67 on the server side and port 68 on the client side. Because broadcast packets don't cross router boundaries by default, networks use a DHCP relay agent — a small forwarding process running on the router that tunnels DHCP messages to a centralized DHCP server on a different subnet.

Key Takeaway

DHCP elegantly solves the bootstrap problem (getting network config when you have no network config yet) by using UDP broadcast. Leases make address allocation both automatic and self-healing: devices that leave simply stop renewing, and addresses flow back to the pool without administrator intervention.

Section 05

DNS: The Internet's Distributed Phone Book

Your browser needs a numeric IP address to send packets, but humans prefer names like cs144.scs.stanford.edu. The Domain Name System (DNS) is a globally distributed, hierarchical database that maps human-readable names to IP addresses (and much more).

Why Not Just a File?

In the early ARPANET days, a single file called HOSTS.TXT was maintained by the Network Information Center and periodically downloaded by every host. This worked for a few hundred machines. With billions of hostnames today, a single file would be gigabytes large, update constantly, and require every host to re-download it — an O(n²) network cost that collapses under its own weight.

DNS's design exploits two key properties of name resolution:

  • 1Read-mostly: names are looked up far more often than they change, enabling aggressive caching.
  • 2Loose consistency acceptable: a name pointing to a slightly stale IP for a few minutes is usually fine (unlike a bank balance). This lets cached answers be reused without global coordination.

The Hierarchical Namespace

DNS Name Tree
                          . (root)
                 ┌────────┼────────┐
                edu      com      org     us    fr
              ┌──┴──┐    ├──┐
          stanford  berkeley  google  cisco
           ┌──┴──┐
          cs    www
          │
         www

Each zone is a subtree delegated to a separate authority. Stanford University controls the stanford.edu zone and can add, remove, or change any name under it without asking anyone. The root zone delegates .edu to Educause, which delegates stanford.edu to Stanford. This hierarchical delegation is what makes DNS decentralized — no single entity controls all names.

Resource Records (RRs)

Every piece of information in DNS is stored as a Resource Record with the format:

DNS Resource Record format
# name   [TTL]  [class]  type    rdata
www.stanford.edu.  3600   IN       A       171.64.64.119
scs.stanford.edu.  3600   IN       NS      ns1.scs.stanford.edu.
cs144.scs.stanford.edu. 3600 IN   CNAME   some-host.stanford.edu.

The TTL (Time to Live) tells resolvers how long to cache this record. A TTL of 3600 means: cache this answer for one hour, then ask again.

How a Resolution Works: Walking the Tree

When your computer looks up www.scs.stanford.edu and has no cached answer, a recursive resolver (usually provided by your ISP or set up via DHCP) performs a tree traversal on your behalf:

  • 1Ask a root server (one of 13 named a–m.root-servers.net, each heavily replicated via anycast): "Who knows about .edu?" → gets NS records for the edu TLD servers.
  • 2Ask the .edu TLD server: "Who knows about stanford.edu?" → gets NS records for Stanford's name servers plus glue records (A records for the name server hostnames themselves, preventing a chicken-and-egg problem).
  • 3Ask Stanford's name server (argus.stanford.edu): "Who knows about scs.stanford.edu?" → gets NS records for the SCS zone.
  • 4Ask the SCS name server: "What is www.scs.stanford.edu?" → gets the A record with the IP address.

The recursive resolver caches every answer along the way according to its TTL. The next person who asks for any *.scs.stanford.edu name benefits from the cached NS records, saving two round trips.

Glue Records: Breaking the Cycle

There's a subtle circular dependency: to find www.stanford.edu you need the IP of argus.stanford.edu (Stanford's name server), but to find that you'd need to ask Stanford's name server — a chicken-and-egg problem. DNS breaks this cycle with glue records: the parent zone (.edu) stores not just the NS record for stanford.edu but also the A record for argus.stanford.edu, allowing bootstrapping without circular dependency.

Name Compression

DNS packets are limited to 512 bytes over UDP. Long names like www.scs.stanford.edu appear repeatedly in a response (in the question, answer, and NS sections). DNS uses pointer compression: any label whose leading byte has its top two bits set (0xC0–0xFF) is interpreted as a 14-bit offset into the packet, pointing to where the full name was spelled out earlier. This compresses repeated domain names to just 2 bytes.

Key Takeaway

DNS is a read-mostly, loosely-consistent, hierarchical distributed database. Its three structural pillars — delegation (zones), caching (TTLs), and glue records — together allow a single authoritative answer to scale to billions of lookups per second globally, without any central coordination.

Section 06

NAT: Network Address Translation

The original vision of the internet: every device gets a globally unique IP address, and any device can communicate with any other device directly — the end-to-end principle. Reality: IPv4 has only ~4 billion addresses, and we ran out. The workaround that became ubiquitous is NAT — Network Address Translation.

The Core Idea

A NAT box sits between a private network (your home or office) and the internet. Devices on the private network use private addresses (e.g., 10.x.x.x or 192.168.x.x) that are not globally routable. The NAT has one (or a few) real public IP addresses.

When a private device (say 10.0.0.101:4512) sends a packet to the internet, the NAT:

  • 1Rewrites the source IP and port to its own public IP and a freshly allocated port: 128.34.22.8:6641.
  • 2Stores a mapping: (128.34.22.8, 6641) ↔ (10.0.0.101, 4512).
  • 3When the reply arrives at port 6641, reverse-translates and forwards to 10.0.0.101:4512.

NAT Behavioral Variants

The different types of NAT differ in which incoming packets they allow through an existing mapping:

Full Cone NAT

Once a mapping exists, any external host can send packets to the mapped port — even ones the internal host never contacted. Most permissive.

Restricted Cone NAT

Only external hosts that the internal host has previously sent a packet to (by IP address) can send back through the mapping.

Port-Restricted Cone NAT

Like restricted, but must also match the specific port the internal host previously contacted.

Symmetric NAT

Creates a new mapping for each unique destination. Packets from server-A:80 and server-B:80 get different mapped ports. Hardest to traverse.

The Problem: Incoming Connections

NAT works beautifully for outbound connections — your laptop opens a TCP connection to Google, and the NAT creates a mapping. But what about inbound connections? If you're running a server on 10.0.0.101:80, nobody on the internet knows how to reach it — your public IP has no established mapping for port 80.

This breaks the end-to-end principle. Pre-Skype VoIP applications like Speak Freely famously failed behind NATs because neither peer could initiate a connection to the other.

NAT Traversal Techniques

  • AStatic port mapping: manually configure the NAT to forward port 80 to an internal host. Used for home servers and game consoles.
  • BConnection reversal: both peers are behind NATs. A mutually-accessible rendezvous server asks the peer that can accept connections to initiate — reversing who "connects" to whom.
  • CRelays: all traffic flows through a public relay server. Always works, but wastes server bandwidth and adds latency. Used as fallback in WebRTC (TURN servers).
  • DNAT hole-punching: both peers simultaneously send packets to each other's public IP:port, causing both NATs to create mappings. If timed correctly, the subsequent packets traverse both NATs. Used by WebRTC, WireGuard, and online games.

Hairpinning

What if device A (10.0.0.101) wants to reach device B (10.0.0.99) using B's external (public) address? A non-hairpinning NAT would drop this traffic; a well-implemented NAT (per RFC 4787) hairpins — it translates the destination back to B's internal address, allowing devices on the same LAN to communicate via their public addresses. Required for mDNS-based applications and certain WebRTC scenarios.

The NAT Debate

NAT is genuinely controversial among networking engineers:

NAT Trade-offs
Advantages                              Disadvantages
──────────────────────────────────────  ──────────────────────────────────────
Conserves IPv4 address space            Breaks end-to-end connectivity
Implicit firewall (no unsolicited       Applications must implement traversal
  inbound traffic reaches devices)        hacks (STUN, TURN, UPnP)

The practical verdict: NATs are here to stay, even as IPv6 eliminates the address scarcity that originally motivated them. Too much infrastructure depends on NAT behavior for it to disappear. IPv6 deployment is slow, and many operators have discovered they actually like the implicit firewall semantics of NAT.

Key Takeaway

NAT extends the life of IPv4 by multiplexing many private addresses behind one public IP using port numbers as a secondary demultiplexer. It introduces fundamental friction for any protocol that requires inbound connections, driving an entire industry of workarounds (STUN, TURN, ICE, UPnP, hole-punching). Understanding NAT behavior is essential for anyone building networked applications.

Summary

The Five Things to Remember

  1. HTTP is a text-based request–response protocol over TCP. HTTP/1.0's one-connection-per-request model pays a full TCP handshake cost for every resource, causing dramatic slowdowns on pages with many assets. HTTP/1.1's keep-alive eliminates redundant handshakes and enables pipelining, achieving ~4× speed improvement on realistic workloads. HTTP/2 adds multiplexed streams to eliminate head-of-line blocking.
  2. BitTorrent turns every downloader into an uploader. Files are split into pieces, each hash-verified. Rarest-first selection preserves swarm availability; tit-for-tat choking rewards contributors; optimistic unchoking discovers better peers. The endgame strategy prevents stalls at the tail of a download.
  3. DHCP solves the bootstrap problem via UDP broadcast. A device with no IP address broadcasts a DISCOVER message, receives OFFERs from servers, selects one with REQUEST, and gets a time-limited ACK. Leases make address reclamation automatic.
  4. DNS is a hierarchically-delegated, read-mostly, cached distributed database. Resolution walks the tree from root → TLD → authoritative zone, with caching at each step according to TTLs. Glue records break the circular dependency between zone delegation and name resolution.
  5. NAT extends IPv4 by rewriting source IPs and ports at a gateway. It works transparently for outbound connections but fundamentally breaks the ability of external hosts to initiate connections to private devices — motivating a family of traversal techniques (hole-punching, relays, STUN/TURN) that underlie nearly every modern real-time communication system.
