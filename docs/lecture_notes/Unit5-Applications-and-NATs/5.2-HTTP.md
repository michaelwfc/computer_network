# HTTP

### HyperText Transfer Protocol

Every time you visit a URL, your browser uses **HTTP — the HyperText Transfer Protocol** — to
ask a server for a document. HTTP is the cornerstone of the web and today powers video streaming,
API calls, and single-page applications. Let's understand it from the ground up.

### What is HyperText?

**HyperText** is a document format expressed in plain ASCII text where special tags (wrapped in
`<angle brackets>`) carry formatting instructions. Think of it as a letter where you write
`<h2>Introduction</h2>` and your browser knows to render the word "Introduction" as a large
heading.

The killer feature of HyperText is **embedding**: a document can reference other documents. An
`<img src="photo.jpg">` tag does not store the image bytes inside the page — it tells the browser
"go fetch this separate file and display it here." This means loading a single page can *trigger
a cascade of additional requests*. Opening the New York Times homepage, for instance, results in
roughly 20 separate resource downloads in the background.

### The HTTP Request–Response Model

HTTP uses a **client–server** architecture. The client (your browser) opens a **TCP connection**
to a server and sends a command. The most common command is `GET`, which asks for a resource at a
given URL. The server reads the request, processes it, and writes back a response — then the cycle
repeats.

Both the request and the response are human-readable ASCII. You can literally type an HTTP request
by hand using the `telnet` tool — something no other widely-used protocol makes quite this easy.

### Request Format

HTTP/1.x request structure 
-first line contains METHOD, URL, and HTTP version
separated by spaces followed by `\r\n`. 
- Zero or more `Header-Name: value\r\n` lines follow.
- A mandatory blank line `\r\n` separates headers from the optional body.

```
GET /fullduplex/index.html HTTP/1.1\r\n     ← request line
Host: sing.stanford.edu\r\n                 ← header
Accept: text/html\r\n                       ← header
\r\n                                         ← blank line (mandatory)
                                             ← body (empty for GET)
```

The first line contains three fields separated by spaces: the **method** (`GET`, `POST`, `PUT`,
…), the **URL path**, and the **protocol version**. Each line ends with a carriage-return +
newline (`\r\n`). A mandatory blank line separates the headers from the optional body (used by
methods like `POST` that send data to the server).

### Response Format

[Diagram: HTTP/1.x response structure — first line contains HTTP version, three-digit status
code, and status phrase followed by `\r\n`. Zero or more header lines follow. A mandatory blank
line separates headers from the response body.]

```
HTTP/1.1 200 OK\r\n                         ← status line
Content-Type: text/html; charset=utf-8\r\n  ← header
Content-Length: 4823\r\n                    ← header
\r\n                                         ← blank line
<!DOCTYPE html>...                          ← body (the actual document)
```

A response starts with a **status code**: `200 OK` (success), `304 Not Modified` (use your
cached copy), `404 Not Found`, `500 Internal Server Error`, etc. These three-digit codes let
clients programmatically react without parsing prose.

### HTTP/1.0 and Its Speed Problem

In HTTP/1.0 the rule is simple: **one request per TCP connection**. After the server sends the
response, it closes the connection. If your page needs ten images, you open ten connections —
each paying the full cost of a TCP handshake.

#### Case 1: Single Page Load

First, there’s the latency of sending a SYN, so 50ms. There’s the latency of the SYN-ACK, so another 50ms. 
On receiving the SYN/ACK, the client can send the ACK of the three way handshake, followed by the request. 
The request has a packetization delay of 10ms, so this takes 60ms. 
The server then needs to send the response back. The packetization delay of the response is 20ms, so this step is 70ms. 

- SYN: 50ms, 
- SYN/ACK: 50ms
- ACK/request: 60ms
- response: 70ms
So the total delay is 50 milliseconds plus 50 milliseconds plus 60 milliseconds plus 70 milliseconds, or 230

sends ACK+GET at t=60ms (adding 10ms packetization delay), receives 200 OK (2 segments) arriving
at t=230ms. Total: 50 + 50 + 60 + 70 = 230 ms.]

```

  │─────────── SYN ──────────────────────►  │  t = 0ms

```

#### Case 2: Page + 2 Images

Step 1 (the page itself) 
Setup: 100ms, request/response: 130ms, costs 230 ms as above. 

Step 2 sends two parallel image requests on two separate TCP connections. 
Setup: 100ms, request/response: 150ms

Even though both connections share the same physical link — meaning their segment transmissions queue up behind each other — the important insight is that **packetization delays partially mask each other**: 
while response 1a goes out, request 2 is arriving, so response 2a queues immediately after response 1b.

Diagram: Two parallel HTTP/1.0 image requests on a shared link. 
After the TCP handshake (100ms),
request 1 arrives at the server at t=160ms and request 2 at t=170ms. 
The server queues four response segments total. They depart sequentially: 
resp 1a at t=170ms, resp 1b at t=180ms,
resp 2a at t=190ms, resp 2b at t=200ms. 
Total step 2: 100ms setup + 150ms data = 250ms.

Grand total: 230 + 250 = 480ms.

Notice: even loading just 2 images *more than doubles* the page load time — largely because we paid the 100 ms TCP handshake cost *again* just to start those image requests.

> **Key Takeaway:** HTTP/1.0's one-connection-per-request model forces a full TCP handshake
> (100 ms at 50 ms RTT) before every burst of resources. This overhead compounds badly as pages
> embed more and more assets. Every repeated setup also restarts TCP's congestion window from
> scratch, preventing the network from warming up.

## HTTP/1.1 Keep-Alive

HTTP/1.1 introduced one of the most impactful optimizations in the history of the web:
**persistent connections**, controlled by the `Connection: keep-alive` header. Instead of tearing
down the TCP connection after each response, the server keeps it open so the client can reuse it
for subsequent requests.

### The Keep-Alive Negotiation

1. The client includes `Connection: keep-alive` in its request header, hinting "please leave this
   connection open after you respond."
2. The server responds with `Connection: keep-alive` (or `Connection: close` if it refuses). It
   may also send a `Keep-Alive: timeout=60` header indicating how long it will maintain the idle
   connection.
3. The client sends further requests on the *same TCP connection*, skipping the handshake entirely.


### Quize 2 : Concrete Speed Comparison
Assumptions for the timing analysis below:

| Parameter | Value |
|---|---|
| One-way latency | 50 ms |
| HTTP request size | 1 full segment (1 ms packetization delay) |
| HTTP response size | 2 full segments (2 ms packetization delay) |
| SYN / ACK packets | 0 ms packetization delay (tiny) |
| Segment packetization delay| 1 ms (request and response), full duplex|
| Max parallel connections | 2 |


With 50 ms latency, 1 ms packetization delay, and a page that loads 11 images:

#### HTTP/1.0

- Page setup: 100ms, request/response: 51 ms+ 52 ms = 103ms
- 11 images. 6 x (image setup: 100ms + request/response: 103ms)


#### HTTP/1.1 

- Connection setup: 100ms
- Page request/response: 103ms
- Image requests/responses: 123m

Requesting the 11 images, however, only takes 123 milliseconds! That’s 51 milliseconds for the first request, and 72 milliseconds for the 11 responses, 50 milliseconds of latency plus 22 milliseconds of packetization delay.



| Phase | HTTP/1.0 | HTTP/1.1 |
|---|---|---|
| TCP handshake(s) | 100ms × 7 rounds = 700ms | 100ms × 1 = 100ms |
| Page request/response | 103ms | 103ms |
| 11 image requests | 6 × 203ms = 1,218ms | ~123ms (pipelined) |
| **Total** | **1,421 ms** | **326 ms** |


HTTP/1.1 is **4× faster** in this scenario. The dramatic gain comes from two sources. 
- First, we pay the TCP handshake only once. 
- Second, we can send all 11 image requests back-to-back on the open connection without waiting for each to fully complete before sending the next — a technique called **request pipelining**.


### Why Persistent Connections Also Help Congestion Control

TCP's congestion control algorithm (AIMD / slow start) begins each new connection with a tiny
window. The window must be earned by sending packets without drops. HTTP/1.0 resets this learning with every new connection. HTTP/1.1 lets the window *carry over* across multiple requests on the same connection, so later requests in a session enjoy a warmed-up, larger congestion window and therefore higher throughput.

### SPDY and HTTP/2

HTTP/1.1's pipelining has a subtle problem: responses must be delivered in the same order as
requests. If a slow-to-generate page is requested first, images must wait — a phenomenon called
**head-of-line blocking**. Google's SPDY protocol (later standardized as HTTP/2) solved this with:

- **Multiplexed streams**: multiple logical request/response pairs interleaved on one connection,
  so a slow resource doesn't block fast ones.
- **Header compression**: browsers send largely identical headers (User-Agent, Accept, cookies) on
  every request; HTTP/2 compresses these, saving meaningful bytes on mobile.
- **Server push**: a server can proactively send resources it knows the client will need, before
  the client even asks.

> **Key Takeaway:** Keep-Alive eliminates per-resource TCP setup cost and allows pipelining. On a
> page with many assets, this single change produces 4× speed improvements. HTTP/2 goes further by
> eliminating head-of-line blocking and adding header compression — both building on the same
> insight: share one long-lived, well-warmed TCP connection rather than opening many short ones.

## Q1：  What are the differences bwteen Hyper text vs xml vs markdown vs pdf?

### Four Formats, Four Fundamentally Different Philosophies

Adding PDF to the mix introduces a completely new dimension: the others are all **source formats** — PDF is a **final presentation format**.

---

### The Core Philosophical Divide

```
Source formats (content + structure, meant to be processed/transformed):
  XML       → structured data for machines
  HTML      → structured documents for browsers
  Markdown  → lightweight prose authoring

Final format (content + exact layout, meant to be displayed as-is):
  PDF       → pixel-precise visual document for humans to read/print
```

This is the most important distinction. The first three are **inputs to a rendering pipeline**. PDF is the **output** — the rendered artifact itself.

---

### What PDF Actually Is

PDF (Portable Document Format, invented by Adobe in 1993) does not describe *structure*. It describes **exact visual appearance** — where every glyph, line, and image appears on a page, measured in precise coordinates.

Inside a PDF, text is not stored as "this is a paragraph" or "this is a heading." It is stored as:

```
Draw glyph 'T' at position (72.0, 720.5) using font Helvetica-Bold 14pt
Draw glyph 'C' at position (82.3, 720.5) using font Helvetica-Bold 14pt
Draw glyph 'P' at position (91.7, 720.5) using font Helvetica-Bold 14pt
...
```

The renderer's job is trivial: paint pixels exactly where told. There is no layout engine, no reflow, no interpretation.

---

### Full Four-Way Comparison

| Property | XML | HTML | Markdown | PDF |
|---|---|---|---|---|
| Primary purpose | Data interchange | Browser rendering | Human authoring | Final presentation |
| Primary consumer | Programs | Browsers | Markdown processors → HTML | Humans / printers |
| Stores structure? | Yes (rich) | Yes | Yes (limited) | No — stores appearance |
| Stores semantics? | Yes (user-defined) | Yes (W3C defined) | Partial | Essentially no |
| Reflowable text? | N/A | Yes | Yes | No — fixed page layout |
| Editable source? | Yes | Yes | Yes | Not meaningfully |
| Copy-paste fidelity | Perfect | Good | Perfect | Often broken |
| Search inside | Yes | Yes | Yes | Approximate (glyph matching) |
| Font/layout control | None | Partial (CSS) | None | Complete and exact |
| File size | Small-medium | Small-medium | Very small | Large |
| Invented | 1996 | 1991 | 2004 | 1993 |

---

### The Rendering Pipeline, Extended

```
Human writes Markdown
        |
        v
  Markdown processor
        |
        v
      HTML
        |
        v
  Browser / print engine
        |
        v
       PDF   ←─── this is where PDF lives: at the END
        |
        v
  Printer or screen
```

PDF is what you get **after** everything else has done its job. Going backwards from PDF to recover the original structure is lossy and unreliable — a common pain point when trying to extract text from PDFs programmatically (as you've experienced with `pdftotext` in your CS144 workflow).

---

### The Critical Weakness of PDF: Lost Semantics

This is worth dwelling on because it has real engineering consequences.

In HTML:
```html
<h1>TCP Slow Start</h1>
<p>cwnd grows exponentially until ssthresh.</p>
```

The tags tell you: "this is a heading," "this is a paragraph." Structure is explicit and machine-readable.

In PDF, the equivalent is stored as something like:
```
[glyph T at x=72 y=740 font=Bold size=18]
[glyph C at x=83 y=740 font=Bold size=18]
[glyph P at x=94 y=740 font=Bold size=18]
...
[glyph c at x=72 y=710 font=Regular size=11]
[glyph w at x=79 y=710 font=Regular size=11]
...
```

There is no machine-readable signal that the first line is a heading. A PDF reader *guesses* based on font size, position, and boldness — which is exactly why `pdftotext` sometimes scrambles column layouts, reorders content, or merges separate text blocks.

---

### When Each Is the Right Tool

**Use XML when:**
- Programs exchange structured data
- You need schema validation and namespaces
- Examples: network device configs, SVG graphics, RSS, Maven build files

**Use HTML when:**
- Delivering content to a web browser
- Building a web application or interactive page
- Examples: websites, web apps, HTML email

**Use Markdown when:**
- A human is writing text-heavy content quickly
- The output target is HTML or a documentation system
- Examples: READMEs, documentation, notes, blog posts

**Use PDF when:**
- The visual appearance must be identical on every device and printer
- The document is a final artifact not meant to be edited
- Examples: academic papers, invoices, legal contracts, CS144 lecture slides

---

### Concrete Example: Same Content, Four Formats

**XML** (machine consumption):
```xml
<algorithm name="slow_start">
  <phase>exponential_growth</phase>
  <trigger>cwnd_lt_ssthresh</trigger>
  <rule>cwnd += 1 MSS per ACK received</rule>
</algorithm>
```

**HTML** (browser rendering):
```html
<section>
  <h2>Slow Start</h2>
  <p>While <code>cwnd &lt; ssthresh</code>, grow exponentially:</p>
  <pre>cwnd += 1 MSS per ACK</pre>
</section>
```

**Markdown** (human authoring):
```markdown
### Slow Start

While `cwnd < ssthresh`, grow exponentially:

```
cwnd += 1 MSS per ACK
```
```

**PDF** — you cannot write PDF by hand in any meaningful sense. A PDF of this content would be a binary file containing font embedding, cross-reference tables, and coordinate-based glyph placement. The closest human-readable approximation of what's inside:

```
BT                          % Begin text
/F1 14 Tf                   % Select font, size 14
72 740 Td                   % Move to position
(Slow Start) Tj             % Draw glyphs
ET                          % End text
BT
/F2 11 Tf
72 710 Td
(While cwnd < ssthresh...) Tj
ET
```

Nobody writes that by hand. You generate PDF from LaTeX, Word, a print engine, or a library like `reportlab` or `wkhtmltopdf`.

---

### The One-Sentence Summary of Each

- **XML**: "Here is structured data. You decide what to do with it."
- **HTML**: "Here is a document. Browser, please render it."
- **Markdown**: "Here is prose I wrote quickly. Convert it to HTML."
- **PDF**: "Here is exactly what this page looks like. Display it identically everywhere."
